# Архитектура и добавление Authorize.Net

## Структура

```text
mock_server/
  app.py                    # Composition root: подключение провайдеров
  core/
    config.py               # Настройки локального сервера
    storage.py              # Общие SQLite-транзакции, без CRM/payment-логики
  providers/
    kommo/
      router.py             # HTTP, Bearer auth, служебное API
      service.py            # Поведение Kommo и операции над сущностями
      data.py               # Типы JSON, начальные данные, проверка состояния
tests/
  test_kommo.py
```

Каждый провайдер создаёт свой APIRouter и владеет своим состоянием. `app.py` явно
подключает роутеры; динамический plugin registry пока не нужен. Маршруты сохраняют
пути upstream API, чтобы приложения переключались через конфигурацию.

`core` не импортирует провайдеры. Kommo не должен импортировать будущий Authorize.Net.
Зависимость между платежом и записью в CRM выполняет настоящее приложение — это и
есть проверяемая интеграция. Эмуляторы не должны обходить её прямыми вызовами друг друга.

SQLite-файл отдельный для каждого провайдера: `kommo.sqlite3`, в будущем
`authorize_net.sqlite3`. Сброс одного не затрагивает другой. `JsonStore[T]` гарантирует
транзакционный read-modify-write и rollback batch-запроса. Бизнес-проверки остаются
в провайдере. Такая модель пригодна для небольших локальных наборов; при росте объёмов
хранение транзакций/профилей Authorize.Net можно реализовать отдельными таблицами.

## Следующий этап: Authorize.Net

В `bestcredit4you/payment/apps/api/src/gateway/authorize-net.ts` шлюз уже использует
HTTP POST с JSON на настраиваемый `config.apiUrl`. Поэтому первая версия mock должна
реализовать JSON-контракт на `/xml/v1/request.api` (название пути не означает, что
текущему клиенту нужен XML). XML можно добавить позже отдельным адаптером при необходимости.

1. Добавить `providers/authorize_net/`: `router.py`, типизированные request/response
   модели, service и собственное хранилище профилей, платежных профилей, транзакций.
2. Подключить APIRouter в `app.py`; добавить настройки тестовых `apiLoginId` и
   `transactionKey`. У Authorize.Net авторизация в JSON-теле, не Kommo Bearer.
3. По текущим вызовам шлюза определить необходимый набор операций. Добавить ответы
   `messages.resultCode` и `transactionResponse` с корректными строковыми кодами и ID.
4. Добавить управляемые сценарии: approved, declined, held, error, duplicate и timeout.
   Выбор сценария через служебное `/_mock/authorize-net/...`, без изменения реальных
   форматов запросов. Сценарии должны быть воспроизводимыми, не случайными.
5. Реализовать жизненный цикл транзакции: approval не равен settlement. Отдельный
   переход состояния и webhook/reconciliation должны проверять поведение worker.
6. Для callback-доставки добавить явную конфигурацию локальных адресатов, журнал
   попыток и повторную доставку. Не держать SQLite-транзакцию во время HTTP-вызова.
7. Проверить реальным `AuthorizeNetClient`, затем end-to-end: payment → mock gateway
   → worker → запись заметки/задачи в mock Kommo.

Этот этап не реализован в текущей версии. Компоненты Kommo уже изолированы так,
чтобы его можно было добавить без изменения существующих API-маршрутов и фикстур.
